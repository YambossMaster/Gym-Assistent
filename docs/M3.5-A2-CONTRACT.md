# M3.5-A2 Contract — App Shell, Auth, and Settings correction

> Frozen 2026-09-12. This Contract implements the approved M3.5-A2 Roadmap scope; it does not
> change Roadmap scope, domain ownership, or any M4+ dependency.

## 1. Coach job and route boundary

A signed-in Coach must be able to move between the existing primary workflows, recognise whose
Workspace is open, and manage identity, Workspace preferences, and account safety without a failed
secondary request blanking an otherwise usable Settings route.

| Surface                                         | Frozen responsibility                                                                                    |
| ----------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| Auth bootstrap, sign-in, registration, recovery | Preserve the existing M2 operation set and six-digit Email OTP behaviour.                                |
| Authenticated shell                             | Present the existing Coach routes and truthful Workspace identity.                                       |
| `/settings`                                     | Edit existing Workspace display name/time zone and operate existing account security/lifecycle features. |

No M4 scheduling, M5 training, availability, reminders, notifications, LINE/OA, or new account
profile fields are introduced. Public capability routes remain M6 work and are outside this package.

## 2. Demo reference and deliberate corrections

The archived Demo establishes the dark desktop rail, compact mobile top bar, four primary mobile
workflow destinations, and Coach identity treatment. Its local-only sync wording, notification
surface, reminder/configuration fields, availability summary, LINE/OA card, and demo-reset controls
are not production features and must not be copied.

The formal Web deliberately differs from the Demo as follows:

- mobile renders one masthead only; it must not render both the desktop rail header and a second
  mobile header;
- Settings remains a header action on mobile, while the persistent bottom navigation contains only
  Today, Calendar, Students, and Exercises;
- the shell displays no connection or sync badge. A signed-in session or a successful query does not
  prove connectivity, synchronization, or a last-sync time;
- Workspace settings are limited to the server-supported display name and IANA time zone.

## 3. Presentation and interaction decisions

### Desktop

At widths above the existing mobile breakpoint, show the dark left rail with brand, all five routes,
and a Coach identity card. The card shows the resolved Coach name, matching initials avatar, and
the signed-in Email. It is informational; it does not add an account menu or a new action.

### Exact 390×844 mobile path

At the mobile breakpoint, remove the desktop rail from layout and accessibility navigation. Render
one compact top header containing the brand and a Settings link, followed by route content and the
fixed, safe-area-aware bottom navigation. The bottom navigation has exactly Today, Calendar,
Students, and Exercises. Settings is deliberately absent from it. Route content retains enough
bottom padding to remain fully readable and actionable above the navigation.

The Settings link, bottom-nav links, forms, retry controls, and destructive dialogs must be
keyboard reachable. When a destructive dialog opens, focus moves to its confirmation input; Escape
or Cancel closes it without action and returns focus to the initiating control. There must be no
horizontal overflow at 390 CSS pixels.

### Coach identity

For every shell location, resolve the label in this order: nonblank Workspace `displayName`, then
the signed-in Email local part, then `教練`. Derive the initials avatar from that same resolved
label, using its first two visible characters in uppercase where applicable. No avatar upload,
Auth user-metadata display name, browser persistence, or additional endpoint is permitted.

The shell may use cached Workspace settings while its query refreshes. Before the first successful
settings response it uses only the Email fallback; if that request fails, it remains usable with the
same fallback and no connection claim.

## 4. Existing data and operation contract

No schema, Module, HTTP route, Auth configuration, or query-key change is required.

| Data/operation                                   | Authority and A2 use                                                                                                                                                                    |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET /v1/workspace-settings`                     | Existing authenticated, Workspace-derived projection: `displayName`, `timeZone`, `version`, `updatedAt`. It drives the shell identity and Workspace settings panel.                     |
| `PATCH /v1/workspace-settings`                   | Existing authenticated, versioned edit of `displayName` and `timeZone`. On success, replace the Coach-scoped settings cache so the shell updates immediately.                           |
| `GET /v1/account-lifecycle`                      | Existing authenticated lifecycle projection. It drives only the deletion-status subpanel.                                                                                               |
| Account deletion request/cancel/immediate delete | Preserve the existing API operations and explicit `DELETE` confirmation. Never infer a Workspace or accept one from the browser.                                                        |
| Supabase Auth actions                            | Preserve Email/password sign-in, Google sign-in/linking, recovery, local sign-out, password update, and the six-digit email-verification flow. Auth administration remains server-only. |

All existing identity, tenant derivation, password requirements, token handling, cache clearing on
sign-out/subject change, and account-lifecycle authority remain unchanged. A2 adds no browser-side
business rule or durable local cache.

## 5. `/settings` state boundaries

`/settings` has three independent boundaries. A failure in one must not conceal the other two.

| Boundary          | Loading                                                                                                                       | Ready / refreshing                                                                                  | Error and recovery                                                                       | Mutation / conflict                                                                                                                                                                                                            |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Workspace profile | Its panel alone shows a semantic loading skeleton.                                                                            | Display-name and time-zone form; cached values remain readable during background refresh.           | Its panel alone explains that Workspace settings could not load and offers retry.        | Disable only its save action while saving; retain typed values on validation/transport failure. A `409` retains the draft, fetches current server data on explicit retry, and requires the Coach to reapply the intended edit. |
| Account security  | No request-dependent route gate; Email, local logout, and password operation remain available from the authenticated session. | Show the signed-in Email, local logout, and the existing password flow appropriate to its identity. | Auth-operation errors remain at the relevant operation and leave other controls usable.  | Disable only the active Auth operation; preserve password input on failure and clear it only after success/cancel.                                                                                                             |
| Account lifecycle | Its subsection alone shows a semantic loading state.                                                                          | Show deletion status plus the existing request/cancel/immediate-delete choices.                     | Its subsection alone offers retry; Workspace profile and account security remain usable. | Disable only lifecycle/deletion controls involved in the action. Every request or immediate deletion requires explicit `DELETE`; successful immediate deletion signs out locally.                                              |

A single shared notice area may report a completed or failed operation, but it must not substitute for
the boundary-specific loading/error/retry state. Refreshing is never presented as a successful
connection or synchronization claim.

## 6. Product-copy slots

Sol owns final styling but uses concise, Coach-facing Traditional Chinese copy in these fixed slots:

- Shell identity: resolved Coach name and signed-in Email only; no status prose.
- Settings page: `設定`, Workspace panel `教練資料`, security panel `帳號安全`, lifecycle action
  `刪除帳號` / `取消刪除` as state requires.
- Boundary errors: explain which panel cannot currently load and offer `重新載入`; never imply data
  loss or an unverified network condition.
- Destructive confirmations: distinguish the reversible 14-day deletion request from immediate,
  permanent deletion; retain the existing explicit-confirmation wording.

No rendered copy may mention M3.5, query/cache state, migrations, implementation status, or future
features.

## 7. Terra implementation and test boundary

Terra may refactor the existing App Shell and Settings route into semantic components, bind the
existing queries/mutations, preserve their Coach-scoped cache behaviour, and add focused tests. It
may not make a new visual, spacing, responsive, interaction-styling, or end-user-copy decision.

Required focused evidence:

1. shell identity selects Workspace name, then Email local part, then `教練`, and avatar initials
   use that same value;
2. no static connection/sync claim remains; cached shell identity survives a settings refresh/error;
3. each Settings boundary independently selects Loading, Ready/Refreshing, Error with retry, and
   relevant mutation/error behaviour;
4. settings update replaces the shared Coach-scoped cache; Auth sign-out/subject change still
   clears private data; six-digit OTP tests remain green;
5. desktop and exact 390×844 browser acceptance proves one mobile masthead, header Settings access,
   four-item bottom navigation, keyboard/focus/dialog behaviour, and no horizontal overflow.
