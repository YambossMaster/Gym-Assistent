# 學生群組與多人共課 Contract（審閱稿）

> 2026-10-20，獨立 Contract 工作線；**尚未凍結，未改 Roadmap，也未授權 Sol、migration 或發布**。本稿以目前 `origin/main` 本地快照 `531f223`、主 checkout 的未追蹤討論稿，以及 2026-10-19 已接受的桌面／手機訓練 UI 範本為依據。正式套件位置與 Contract 凍結由 Product Owner 決定；不能把 UI 原型當成資料庫證據。

> 2026-10-20 Product Owner 修訂方向：**學生群組就是現有學生主體的一種集合型態**，沿用原有購課、排課、課堂、訓練、場地及收支路徑，只對多人名單與組數歸屬做必要擴充。方案學生人數始終只算自然人；群組不增加人數，同一人加入多組也不重算。

## 1. 工作、範圍與交付清單

私人教練固定帶二至三位既有學生共課，需以一個群組購課、排課、扣一堂及記一筆收入／場地成本；每人仍保有自己的出席、訓練結果與成長軌跡。群組是既有學生主體的**集合型態**，在業務流程中像獨立學生一樣使用自己的課包、單堂價、排課與歷史，但不是另一個自然人或學生帳號。既有個人課、歷史與 M3–M8 已交付流程保持有效。

本工作包的已知交付面向共 **8 項**：①群組／成員管理與封存，②群組購課與單堂價格，③一次及週期排課、名單快照，④出席、完課、扣堂和場地／收支，⑤動作優先的多人訓練輸入與個人成長，⑥整堂公開成果／改期，⑦個人封存一致性修正及相容匯出，⑧權限、遷移、手機／桌面與正式交付驗證。此稿完成產品規則與驗證清單的設計；八項實作及其證據均未開始。

不包含開放報名小班、候補、按人販售名額、多教練、學生登入、成員分帳、自動向學生收款、按人計場地費、持久共享訓練計畫或重寫 Demo。群組購課不轉移或消耗個人課包。

## 2. 群組和課堂的權威事實

- 教練從**同 Workspace 的既有自然人學生**建立有名稱、狀態及版本的群組。每組最多三人；一人可屬多組。建立與排課時至少一名有效成員，介面以二至三人共課為主要情境。成員可增減，群組可改名或封存；過去課堂的參與名單、購課或結果不改寫，名稱顯示沿用既有學生重新命名的行為。群組不計入方案學生人數，同一自然人只按其學生身分計一次。
- 加入／移出成員是一次版本化交易：改現行名單，並同步該群組所有**開始時刻晚於伺服器現在時間且仍 scheduled** 的單次和已產生週期課參與名單。若移出後某堂未來課變成零名有效參與者，同交易取消該堂並在確認前顯示數量。已開始、逾時未完成、完成或取消的課堂不改。未來週期課尚未產生的發生次數，產生時用當時群組名單；群組無有效成員時不再生成新課。並行衝突整次回滾，回傳最新群組與受影響課堂狀態供重試。
- 一次共課只是一筆 Course Session：一個起迄時段、場地、狀態、版本、群組權益主體與扣堂來源。參與者是該 Session 的快照，含每人出席狀態；暫時缺席不移出群組。改期移動整堂，既有時段／場地衝突只依原警示政策處理。
- 建立課時名單預設「待確認／出席」；教練在訓練工作區直接切換每人出缺席。完成課前出缺席是可恢復的草稿；完成課時以同一命令確認最終名單與出席。若有人缺席仍選擇「完成上課」，依教練決定扣**群組一堂**，全員缺席也相同。取消或刪除未完成課不扣。缺席是出席事實，不能充當欠費或移除成員訊號。
- 封存群組或**個人學生**時，一次版本化交易將對象設非使用中，停用其使用中的固定課表，取消開始時刻仍在未來的 scheduled 課堂。已開始、逾時未完成、完成和原已取消課維持原樣。封存前顯示將停用的固定課表及取消的課堂數；恢復使用中不自行重建課或啟用週期。封存個人學生時，同一交易停用其現行群組成員資格並從未來群組參與名單移除，保留過去成員關係和結果；若因此某堂未來群組課無有效參與者，該堂取消並提示教練。恢復學生使用中不自動重加群組。此處是對既有學生封存行為的**新修正**，非已交付 M4 的現行行為。
- **群組刪除邊界（Product Owner 已決定）**：已有任何購課、課堂、固定課表或訓練／財務來源的群組只能封存，不能走既有學生硬刪的級聯路徑；尚無上述正式資料的空白群組可沿用學生刪除入口與版本確認。群組成員的加入紀錄本身不阻止刪除空白群組。自然人學生的既有刪除操作須清理其群組成員、參與與本人組數，並使受影響的公開成果失效；**不得因此刪除群組 Session、其他成員的組數、群組課包或場地／收支來源**。這是對一堂多人共用資料的必要保護。

## 3. 課包、單堂計價、場地和財務

- 群組有獨立的單堂參考價、一般及指定場地手動課包。排課不要求預購，也不預扣堂或入帳。完成時沿用 M8-D 來源選擇：可用的該場地群組課包優先，其次通用群組課包；其他既有排序、日期及版本規則不變。不能取成員個人的權益。
- 無可用群組課包而有群組單堂價時，完成課建立一筆與 Session 唯一連結的單堂購課／收入；無價格則完成但標示待補金額。明確的零元價格與缺價不同。日後新增課包或修改參考價不靜默改動已完成來源。重開、取消、購課修正遵守既有來源回復與版本規則。
- 每堂只有一筆場地課程紀錄；租金、預購場地堂數或抽成對這一堂計一次。教練記錄的群組購課收入不拆到成員，產品不推斷實際收款人。Venue 的「場地供客／自帶客」沿用現有購課、固定課表及 Session 上的 `customerSource` 和儲存規則，群組課把**群組主體**當作既有的學生單位來設定，不能從各成員的標記推測或按人數乘算。不另建場地來源欄位或計價引擎。

## 4. 訓練工作區、儲存和個人歷史

這節取代 2026-10-18 討論稿「先選學生表單、每次新增動作選單人／全體」的設計。已接受的 [`GROUP-TRAINING-ACTION-FIRST-PROTOTYPE.md`](GROUP-TRAINING-ACTION-FIRST-PROTOTYPE.md) 和 [`GROUP-TRAINING-MOBILE-PWA-DESIGN.md`](GROUP-TRAINING-MOBILE-PWA-DESIGN.md) 是視覺／互動基準；正式值與命令仍由本 Contract 和 API 決定。

- 從同一個 `/sessions/:id` 工作區記錄：**一份依動作排列的本堂草稿、每人的組數及結果**。`按時序`依各組建立順序顯示，`按學生`把同一批組數依人分區；切換只改投影與本機偏好，絕不新增或重寫紀錄。重複加入同一動作須有不同 occurrence ID。新增動作直接建立一個本堂共享 occurrence，出席者各有新增組入口；不彈單人／全體範圍對話框，也不建立空白的虛構個人成績。
- 每組保有穩定的學生 ID、所屬動作 occurrence、全域建立順序、原本的量測／RPE／結果，並呈現由本人先前組數推得的組號。新組只複製**同一動作、同一學生**上一組的安排值，不複製別人的負重或已完成結果。操作與桌面、390px、320px 欄位布局沿用已接受的 UI 範本；手機保留既有訓練分頁、單行組數格線與底部完課動作。
- 點今日出席的學生入口直接切換出缺席。缺席時其新增入口與組數暫隱，未完成草稿值保留；恢復出席可看到原值。現有**一堂一份 Training Record** 同時保存本堂動作、教練筆記與尚未完成的組數草稿；完成課的原子命令不把缺席者的隱藏組數納入正式個人成長或公開成果，並移除未採用的缺席組數。若缺席者已有輸入，完課確認處明示其結果不會納入。全員缺席時可完成並扣群組一堂，但沒有個人成績。
- 群組 Session 仍只有原本的一份 Training Record、版本與本堂教練筆記；原 `training_exercise` 就是共享動作 occurrence，原 `training_set` 按建立順序保存多人的組數，**只為群組組數增加所屬學生 ID**。編輯一人的組數不覆蓋另一人。沿用既有 `/v1/sessions/:sessionId/training` GET／PUT 和 `/training/complete`、`recordVersion`、`sessionVersion` 與 `operationId`：在既有請求／回應內加群組參與者、出席與組數歸屬欄位，而非建立第二套多人訓練 API 或每人多份記錄。群組儲存需在同一交易核對所有組數的學生是該堂參與者；出席與完課同一原子命令，衝突保留本機未送出的輸入。個人課的原有 payload 與結果維持相容。
- 學生頁的歷史與成長查詢加入此人**出席且有本人組數**的群組課，僅按 `training_set` 的歸屬 ID 取本人數值；不能把同伴組數當成本人成績。組數在既有 scheduled／completed 階段進入成長查詢的時機不另改規則。完課後教練若修正出缺席，沿用版本化訓練儲存：改為缺席須確認移除該人結果並失效舊成果連結；改回出席可重新輸入，但不憑空恢復已移除的組數。同一堂在群組頁和個人頁共用 Session／Training Record ID，不雙計教練時段或場地。群組詳細頁有整堂訓練歷史；混合多人數值沒有單一的「群組最佳成績」，個人成長圖仍按自然人各自計算。

## 5. 路由、介面狀態和公開能力

`/students` 名單的切換選項固定為 **「學生」／「學生群組」／「已封存」**：前兩者各只列使用中的自然人或群組，「已封存」同時列兩類已封存主體，並明示每列型態。搜尋、數量與空狀態依目前選項運作；新增入口依選項建立個人或群組，不把群組算進方案學生人數。

群組有自己的**詳細頁呈現**，沿用 `/students/:id` 及現有學生詳細頁、購課入口的架構，不新增 `/groups` 路由或 App Shell 主導覽。群組頁保留與個人頁對應的五個區塊，但內容依權益與成員歸屬分開：

| 群組頁區塊   | 對應的內容與導航                                                                                                                                                                                                                   |
| ------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 基本資料     | 群組名稱、適用的共同資料與目前成員；每位成員可進入其 `/students/:id` 個人頁，可在此管理群組成員；不顯示群組不適用的個人聯絡欄位。                                                                                                  |
| 固定課程時間 | 以群組這一列 `student_id` 沿用單一學生的固定排課流程；每次產生的課堂仍是一筆群組 Session，參與名單依當時成員快照。                                                                                                                 |
| 運動表現     | 顯示**各成員自己的個人運動表現**及進入各人「個人運動表現」的入口，不建立群組的加總數值、平均值或混合曲線；每人的個人表現含可歸屬於本人的個別課與群組課組數。                                                                       |
| 課程紀錄     | 群組以 Session owner 顯示該群組的課；個人頁則同時顯示本人個別課及其參與的群組課。兩邊的同一堂使用**相同 Session ID**，連到同一 `/sessions/:id`，不複製課堂、扣堂或場地／收支來源。個人列表中的群組課明示群組名稱及本人的出席狀態。 |
| 購課紀錄     | 群組只顯示及管理以群組為權益主體的購課、單堂來源和餘額；個人頁只顯示及管理以該自然人為權益主體的購課和餘額。即使個人參與群組課，也不把群組購課合併到他的購課紀錄。                                                                 |

個人課程紀錄按該堂參與者快照投影，而非僅按 `course_session.student_id`；離開群組或封存後，既有個人課程紀錄仍指向原 Session，未加入前與退出後未參與的課不補入。已完成課中缺席的參與者仍在本人課程紀錄保留該堂，明確標示「缺席」，並連到相同 Session；缺席不產生本人的正式訓練成績，也不改變只扣群組一堂的權益歸屬。Calendar 原有對象選擇器可選群組列，卡片及 Session 頁顯示群組名稱與該堂名單。Demo 沒有群組路由，僅借既有學生、行事曆及訓練頁的資訊層級與交互方式。

各入口沿用現有 Loading、Empty、Not Found、Error、Refreshing、Mutating、Conflict 邊界；局部失敗不清空其他區塊，安全可恢復輸入保留。封存、全員缺席完課、缺價、課包餘額不足、場地封存、成員或 Session 版本衝突須有可執行的下一步。群組沿用名稱、共同訓練目標（既有 `goal`）、教練私有備註、預設場地、單堂價、購課及排課等適用的學生欄位；電話、年齡、LINE 等自然人聯絡欄位對群組不適用，不在群組表單顯示或透過 API 填入。

教練可為一堂群組課建立**一份成果、一個連結**，由持有者看到該堂各出席者的允許動作／組數與缺席標記。教練明確決定是否分享及是否包含本堂教練筆記；沿用期限、撤銷、重發、無快取和欄位 allowlist。任一參與者、出席、動作、已分享結果或筆記的權威版本改動，都讓舊成果連結失效。不得輸出個人長期軌跡、購課、收入、私有學生資訊或 Workspace。群組改期能力連結移動整堂，不允許持有人移動其中一人；課堂取消／封存需使該能力失效。

## 6. 現有架構的最小完整延伸

目前 `lesson_purchase`、`course_session`、`schedule_series`、`session_lesson_source` 與場地／Finance 以同一 `student_id` 指向權益主體。**採用 Product Owner 的最小延伸方向**：在現有 `student` 增加不可變的 `person | group` 種類，既有列全部預設 `person` 並保留原 ID；一個群組是一列 `group`，同樣有名稱、goal、active、version、私有備註、預設場地、單堂價及自己的權益。只新增同 Workspace 的群組成員關係，群組不能加入群組。原購課、課堂、固定課表、完課來源與 Finance 的 `student_id` 不換成另一套 owner 外鍵。人身聯絡欄位對 `group` 固定為不適用值；瀏覽器與 API 型別明示種類，不把群組當成自然人。

在 `student.kind` 之外，必要新增三類權威事實：①群組與自然人成員關係；②群組 Session 的參與者／出席快照；③群組 `training_set` 的所屬自然人 ID。既有 `training_record` 的 `(workspace_id, session_id)` 唯一限制、`training_exercise` 的共享動作及 `training_record.private_note` **維持原狀**，不另建群組紀錄、動作或筆記表。`training_set.position` 繼續作該動作內的全域建立順序，每人的組號由同動作中本人先前組數推得；既有個人課組數的所屬 ID 可為 null 並從 Session owner 判定，無須回填全表。群組課組數必須有屬於該 Session 參與名單的自然人 ID。所有新關聯需同 Workspace 約束；瀏覽器不提交 Workspace ID。

沿用現有 `GET/PUT /v1/sessions/:sessionId/training` 及 `/training/complete`，並擴充既有回應與 payload 以攜帶名單、出席及每組歸屬；沿用同一筆 `recordVersion`、`sessionVersion`、`operationId` 和既有原子儲存交易。群組建立／修改可擴充現有 `/v1/students` 與 `/v1/students/:id` 的請求和回應，成員同步未來課需在同一權威操作中完成；課包、排課、Finance 與公開能力原路由維持。只有在現有路由無法安全表達一個完整操作時才增加窄範圍 endpoint，並在 Sol 前記錄具體原因。個人成長 SQL 現用 `course_session.student_id`，群組課須以本人 `training_set` 歸屬及出席快照補上；公開成果仍讀一份 Training Record，但按人投影組數並在任何相關內容／出席變動時使舊連結失效。

| 原有入口或資料                                                            | 群組所需的最小變更                                                                                      |
| ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------- |
| `student`、`/v1/students`、`/v1/students/:id`、`/students/:id`            | 加 `kind` 和成員欄位／區塊；同一名單、詳細頁與版本化更新流程，不另建群組 CRUD。                         |
| `lesson_purchase`、`course_session`、`schedule_series`、單堂來源、Finance | `student_id` 直接指群組列，維持原本的購課、排課、完課及結算命令；Session 建立及週期生成時補參與者快照。 |
| `training_record`、`training_exercise`、`training_set`                    | 維持一堂一份記錄、一個動作 occurrence 和同一組數集合；只擴充群組組數歸屬與出席資料、驗證及讀取投影。    |
| Training GET／PUT／complete、Public Access                                | 使用原路由、交易、版本和能力連結；群組分支投影每位學生的組數並維持一堂一個連結。                        |

| `postgres-plan-access-repository.ts` 與 HTTP `create-student` gate 計算／限制 active `student` | 僅 `person` 計數；已達學生名額但尚未 overCapacity 時，建立群組不新增自然人，不能誤判為超額；原有真正 overCapacity 的全域寫入限制維持。      |
| `StudentModule`、`postgres-student-repository.ts` 的更新與刪除只以 ID／版本定位                | 同一路由依 `kind` 呈現／驗證適用欄位，限制種類變更；有正式資料的群組只可封存；自然人刪除只清本人群組資料，不得級聯刪群組課與其他人成果。    |
| Scheduling、M8-D 來源、Venue／Finance 用 `student_id` 作權益主體                               | 延續同一受型別約束的 owner ID；群組 Session 一筆，參與者另表；Venue customer source 沿用群組列／Session／Purchase 現有值，不推測成員。      |
| Training SQL 用 `course_session.student_id` 和每堂單份 `training_record`                       | 保留每堂單份記錄與原 API；群組組數加本人 ID；個人成長及 defaults 依本人組數查詢，不混合其他成員。                                           |
| Public Access 以單份 record version 和單一 student name 呈現                                   | 保留一個連結與記錄版本；群組投影須以名單與本人組數呈現，出席／名單變動也要失效舊連結；單人連結維持舊投影。                                  |
| `export-module.ts` 以 Session owner 當個人匯出歸屬；完整匯出另用 Student roster                | 個人訓練／成長匯出改以 participant／set owner 過濾；完整 Workspace 匯出／還原包含群組、成員、課包、課堂、成果；不把 group ID 算成自然人數。 |
| Today、通知、外部行事曆及 Demo import 假設 Session owner 名稱是學生                            | 只在群組課顯示群組名稱與安全的名單摘要；歷史 Demo 匯入只建立 `person`，既有個人通知規則不從群組列推送到任何學生帳號。                       |

以上定位說明前端可沿用已接受的 Training Workspace 和大多數原 API，但**不是只串線**：至少要在資料庫保存成員、課堂名單和組數歸屬，並修正個人成長、公開投影與匯出。Sol 第一個小步是逐查詢核對種類和歸屬，並檢查新欄位／關係約束；只有直接證據顯示受型別約束的既有主體仍無法保持隔離時，才把具體失敗與替代方案帶回 Contract，不預先重建整個系統。

不建立兩三筆隱藏的一對一 Session、每人多份 Training Record、第二套扣堂或收支帳本，不從 UI 原型的假資料／`skippedStudentIds` 推導正式欄位。遷移保留所有既有 ID、權益、歷史和金額；既有單人組數仍由原 Session owner 歸屬，不猜測舊課為群組，也不重算舊餘額。資料刪除、完整 Workspace 匯出／還原和個別學生匯出須各自定義群組歸屬；個別學生匯出只含此人可歸屬的共課組數，不含同伴私有資料。Supabase 私有 schema、API 角色權限、跨 Workspace 404 與公開連結 allowlist 均維持現有邊界。

## 7. Contract 凍結前的決定與工程檢查

1. **Roadmap 歸屬與順序（Product Owner）**：建議獨立的「學生群組」Contract → Sol → CI 套件，在已交付的個人課與 M8-E 支付主幹之外並行；共用 migration／Module 接口的整合須序列化。現行 Roadmap 第 6 節禁止新增編號插入 M10 以前，下一個新階段須由 M11 起命名；數字階段同時代表整合／發布次序，而 M9、M10 尚未完成／決定。因此 PO 須同時選定群組套件的階段與對 M9／M10 的整合次序，不能只命名 M11 就默認可提前發布。此稿不自行編號或更改已核准 Roadmap。只有 PO 批准套件位置及凍結此 Contract 後才可進 Sol。
2. **現有結構的工程檢查**：第 6 節已把「群組也是學生主體」與「一堂一份 Training Record」定為本 Contract 的基線。Sol 起始時須完成逐查詢清單、DB 約束與無資料變更的 migration 設計檢查；若出現具體不能安全沿用的路徑，先提出該路徑的最小修正及證據，只有修正仍不足才回 Contract 討論替代主體。這不是待 PO 重新選擇架構的假設題。

## 8. Sol 與 CI 驗收矩陣

| 風險／流程           | 決定性證據                                                                                                                                                                        |
| -------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 成員變動、封存／刪除 | 加／移成員更新未來單次及週期課；已開始、逾時、歷史不變；個人／群組封存原子停用 Series、取消未來課；恢復不自動重建；有正式資料的群組硬刪被拒，自然人刪除不移除同堂其他人的成果。   |
| 出席、完課與權益     | 三人中一人或全員缺席仍只扣群組一堂；取消未完成不扣；缺席者的個人課程紀錄保留同一 Session 並標明缺席，缺席草稿可恢復但完成後不成個人成績；個人課包不被扣。                         |
| 價格、場地與財務     | 指定場地／通用群組課包優先、單堂備援、缺價與零價分開；每堂一筆場地費／佣金；customer source 明確；重開與修改來源可追溯。                                                          |
