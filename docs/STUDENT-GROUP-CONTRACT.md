# 學生群組與多人共課 Contract（審閱稿）

> 2026-10-20，獨立 Contract 工作線；**尚未凍結，未改 Roadmap，也未授權 Sol、migration 或發布**。本稿以目前 `origin/main` 本地快照 `531f223`、主 checkout 的未追蹤討論稿，以及 2026-10-19 已接受的桌面／手機訓練 UI 範本為依據。正式套件位置與 Contract 凍結由 Product Owner 決定；不能把 UI 原型當成資料庫證據。

## 1. 工作、範圍與交付清單

私人教練固定帶二至三位既有學生共課，需以一個群組購課、排課、扣一堂及記一筆收入／場地成本；每人仍保有自己的出席、訓練結果與成長軌跡。群組是教練管理單位，不是學生帳號或收款人。既有個人課、歷史與 M3–M8 已交付流程保持有效。

本工作包的已知交付面向共 **8 項**：①群組／成員管理與封存，②群組購課與單堂價格，③一次及週期排課、名單快照，④出席、完課、扣堂和場地／收支，⑤動作優先的多人訓練輸入與個人成長，⑥整堂公開成果／改期，⑦個人封存一致性修正及相容匯出，⑧權限、遷移、手機／桌面與正式交付驗證。此稿完成產品規則與驗證清單的設計；八項實作及其證據均未開始。

不包含開放報名小班、候補、按人販售名額、多教練、學生登入、成員分帳、自動向學生收款、按人計場地費、持久共享訓練計畫或重寫 Demo。群組購課不轉移或消耗個人課包。

## 2. 群組和課堂的權威事實

- 教練從**同 Workspace 的既有自然人學生**建立有名稱、狀態及版本的群組。每組最多三人；一人可屬多組。建立與排課時至少一名有效成員，介面以二至三人共課為主要情境。成員可增減，群組可改名或封存；不改寫歷史課堂的名稱、名單、購課或結果。群組不計入學生方案人數，同一自然人只按其學生身分計一次。
- 加入／移出成員是一次版本化交易：改現行名單，並同步該群組所有**開始時刻晚於伺服器現在時間且仍 scheduled** 的單次和已產生週期課參與名單。已開始、逾時未完成、完成或取消的課堂不改。未來週期課尚未產生的發生次數，產生時用當時群組名單。並行衝突整次回滾，回傳最新群組與受影響課堂狀態供重試。
- 一次共課只是一筆 Course Session：一個起迄時段、場地、狀態、版本、群組權益主體與扣堂來源。參與者是該 Session 的快照，含每人出席狀態；暫時缺席不移出群組。改期移動整堂，既有時段／場地衝突只依原警示政策處理。
- 建立課時名單預設「待確認／出席」；教練在訓練工作區直接切換每人出缺席。完成課前出缺席是可恢復的草稿；完成課時以同一命令確認最終名單與出席。若有人缺席仍選擇「完成上課」，依教練決定扣**群組一堂**，全員缺席也相同。取消或刪除未完成課不扣。缺席是出席事實，不能充當欠費或移除成員訊號。
- 封存群組或**個人學生**時，一次版本化交易將對象設非使用中，停用其使用中的固定課表，取消開始時刻仍在未來的 scheduled 課堂。已開始、逾時未完成、完成和原已取消課維持原樣。封存前顯示將停用的固定課表及取消的課堂數；恢復使用中不自行重建課或啟用週期。封存個人學生時，同一交易停用其現行群組成員資格並從未來群組參與名單移除，保留過去成員關係和結果；若因此某堂未來群組課無有效參與者，該堂取消並提示教練。恢復學生使用中不自動重加群組。此處是對既有學生封存行為的**新修正**，非已交付 M4 的現行行為。

## 3. 課包、單堂計價、場地和財務

- 群組有獨立的單堂參考價、一般及指定場地手動課包。排課不要求預購，也不預扣堂或入帳。完成時沿用 M8-D 來源選擇：可用的該場地群組課包優先，其次通用群組課包；其他既有排序、日期及版本規則不變。不能取成員個人的權益。
- 無可用群組課包而有群組單堂價時，完成課建立一筆與 Session 唯一連結的單堂購課／收入；無價格則完成但標示待補金額。明確的零元價格與缺價不同。日後新增課包或修改參考價不靜默改動已完成來源。重開、取消、購課修正遵守既有來源回復與版本規則。
- 每堂只有一筆場地課程紀錄；租金、預購場地堂數或抽成對這一堂計一次。教練記錄的群組購課收入不拆到成員，產品不推斷實際收款人。Venue 的「場地供客／自帶客」若依現行 `student_id` 判定，群組課須有**該堂單一明確來源選擇與快照**，不能從兩三名成員的標記猜測；預設遵守現有場地規則並在完課前讓教練確認。這是群組財務不可省略的新增欄位／操作。

## 4. 訓練工作區、儲存和個人歷史

這節取代 2026-10-18 討論稿「先選學生表單、每次新增動作選單人／全體」的設計。已接受的 [`GROUP-TRAINING-ACTION-FIRST-PROTOTYPE.md`](GROUP-TRAINING-ACTION-FIRST-PROTOTYPE.md) 和 [`GROUP-TRAINING-MOBILE-PWA-DESIGN.md`](GROUP-TRAINING-MOBILE-PWA-DESIGN.md) 是視覺／互動基準；正式值與命令仍由本 Contract 和 API 決定。

- 從同一個 `/sessions/:id` 工作區記錄：**一份依動作排列的本堂草稿、每人的組數及結果**。`按時序`依各組建立順序顯示，`按學生`把同一批組數依人分區；切換只改投影與本機偏好，絕不新增或重寫紀錄。重複加入同一動作須有不同 occurrence ID。新增動作直接建立一個本堂共享 occurrence，出席者各有新增組入口；不彈單人／全體範圍對話框，也不建立空白的虛構個人成績。
- 每組保有穩定的學生 ID、所屬動作 occurrence、全域建立順序、個人在該動作內的組號及原本的量測／RPE／結果。新組只複製**同一動作、同一學生**上一組的安排值，不複製別人的負重或已完成結果。操作與桌面、390px、320px 欄位布局沿用已接受的 UI 範本；手機保留既有訓練分頁、單行組數格線與底部完課動作。
- 點今日出席的學生入口直接切換出缺席。缺席時其新增入口與組數暫隱，未完成草稿值保留；恢復出席可看到原值。**儲存中的草稿與已完成的正式結果須分層**：完成課的原子命令不把缺席者的隱藏草稿發布成個人 Training Record、成長軌跡或公開成果；成功後清除該堂未採用的缺席草稿。若缺席者已有輸入，完課確認處明示其結果不會納入，避免看不見的資料被當成已發布。全員缺席時可完成並扣群組一堂，但沒有個人成績。
- 同一 Session 每個實際出席學生最多一份個人結果。共享動作 occurrence、順序與本堂教練筆記各只有一份權威資料；個人量測和結果分存，編輯一人不覆蓋另一人。草稿 autosave 可用聚合版本或受影響記錄版本，但一次涉及多人的變更、出席切換及完課必須是原子命令；衝突回傳可重讀的伺服器現況，保留本機尚未送出的輸入。離線／重試沿用 M5 的窄範圍草稿規則，不宣稱未確認寫入已儲存。
- 學生頁的歷史與成長查詢加入此人**實際出席且有個人結果**的群組課，從不讀同伴結果；同一堂在群組頁和個人頁共用 Session ID，不雙計教練時段或場地。群組本身沒有混合的個人成長曲線。

## 5. 路由、介面狀態和公開能力

`/students` 增加清楚的「學生／群組」入口；群組清單與詳細頁採 `/groups`、`/groups/:id`，不另增 App Shell 主導覽。群組詳細頁顯示名稱、成員、課包／單堂價、餘額、最近和未來課、歷史；購課仍在此脈絡。Calendar 建課時以「學生／群組」選擇對象，卡片及 Session 頁顯示群組名稱和該堂快照名單。個人學生頁可找到自己的群組共課，但不把其他人資料放進其個人成長區。Demo 沒有群組路由，僅借既有學生、行事曆及訓練頁的資訊層級與交互方式。

各入口需處理首次 Loading、Empty、Not Found、Error、Refreshing、Mutating、Conflict；局部失敗不清空其他區塊，安全可恢復輸入保留。封存、全員缺席完課、缺價、課包餘額不足、場地封存、成員或 Session 版本衝突須有可執行的下一步。Group 與 person 顯示型別必須分清，群組不能出現在個人電話、年齡、私人學生備註或個人額度表單。

教練可為一堂群組課建立**一份成果、一個連結**，由持有者看到該堂各出席者的允許動作／組數與缺席標記。教練明確決定是否分享及是否包含本堂教練筆記；沿用期限、撤銷、重發、無快取和欄位 allowlist。任一參與者、出席、動作、已分享結果或筆記的權威版本改動，都讓舊成果連結失效。不得輸出個人長期軌跡、購課、收入、私有學生資訊或 Workspace。群組改期能力連結移動整堂，不允許持有人移動其中一人；課堂取消／封存需使該能力失效。

## 6. 現有架構的最小完整延伸

目前 `lesson_purchase`、`course_session`、`schedule_series`、`session_lesson_source` 與場地／Finance 以同一 `student_id` 指向權益主體。候選實作是為 `student` 加**受約束的 `person | group` 種類**，既有列全部維持 `person` 和原 ID；群組列只是內部權益主體，不是產品的 Student，也不得被個人路由當成自然人。它可以重用購課、排課、扣堂、單堂與場地來源邏輯，但需在 API 型別、查詢、方案人數、匯出、刪除與公開投影加上明確分流。群組的人身欄位應受資料庫約束為不適用值，而非依賴前端隱藏。**若逐路徑稽核發現無法可靠隔離，改用獨立 group 主體及明確互斥外鍵；不能為了少改欄位而容忍群組污染個人資料。**此選型在 Contract 凍結前須做只讀影響清單與設計檢查，未經驗證不得宣稱最小方案已成立。

必要新增：同 Workspace、不得巢狀的群組成員關係；Session 參與者／出席快照；一堂共享動作 occurrence 與穩定排序；每人最多一份結果及相應版本；一份群組本堂筆記。既有 `training_record` 的 `(workspace_id, session_id)` 唯一限制須調整為每 Session／出席人唯一且保留個人課單份規則。個人成長 SQL 現用 `course_session.student_id`，須改以個人結果及參與者求本人；公開成果目前以單份結果版本失效，須升級成涵蓋整堂參與者、共享動作、全部個人結果及筆記的版本。所有新關聯需同 Workspace 複合外鍵與交易約束；瀏覽器不提交 Workspace ID。

目前 Main 的只讀影響檢查顯示此候選**可作為 Sol 起點，但不是零改動**：

| 現行人身假設                                                                    | 必要修正與關閉條件                                                                                                                                     |
| ------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `postgres-plan-access-repository.ts` 計算所有 active `student` 列               | 僅 `person` 計數；同一人跨組不重算，群組增減不能繞過或誤耗方案額度。                                                                                   |
| `StudentModule`、`postgres-student-repository.ts` 的更新與刪除只以 ID／版本定位 | 個人路由必須限制 `person`，群組路由只處理 `group`；DB 層保護類型不變與群組人身欄位；學生硬刪須先處理群組成員關係，不能級聯刪除群組購課與歷史。         |
| Scheduling、M8-D 來源、Venue／Finance 用 `student_id` 作權益主體                | 延續同一受型別約束的 owner ID；群組 Session 一筆，參與者另表；Venue customer source 取 Session／Purchase 的明確值而不推測成員。                        |
| Training SQL 用 `course_session.student_id` 和每堂單份 `training_record`        | 個人成長改依本人結果；共享 occurrence／本堂筆記另存；個人課單份、群組課每出席人一份的約束與查詢同時成立。                                              |
| Public Access 以單份 record version 和單一 student name 呈現                    | 群組專用的 Session allowlist 投影及整堂版本失效；單人連結維持舊投影，跨 Workspace／猜 token 不可見。                                                   |
| `export-module.ts` 以 Session owner 當個人匯出歸屬；完整匯出另用 Student roster | 個人訓練／成長匯出改以 participant／record owner 過濾；完整 Workspace 匯出／還原包含群組、成員、課包、課堂、成果；不把 group ID 輸出成自然人 Student。 |
| Today、通知、外部行事曆及 Demo import 假設 Session owner 名稱是學生             | 只在群組課顯示群組名稱與安全的名單摘要；歷史 Demo 匯入只建立 `person`，既有個人通知規則不從群組列推送到任何學生帳號。                                  |

以上定位足以否定「只改訓練頁即可開發」。正式 Sol 的第一個小步是補完逐查詢／路由的清單和 schema 約束設計，再做無資料變更的 migration 檢查；若任一自然人假設無法可靠隔離，就在寫入正式群組資料前切換為獨立主體方案。

不建立兩三筆隱藏的一對一 Session，不另寫群組扣堂或收支帳本，不從 UI 原型的假資料／`skippedStudentIds` 推導正式欄位。遷移保留所有既有 ID、權益、歷史和金額；既有單人 `training_record` 的 person ID 只可從其原 Session 精確回填，不猜測舊課為群組，也不重算舊餘額。資料刪除、完整 Workspace 匯出／還原和個別學生匯出須各自定義群組歸屬；個別學生匯出只含此人可歸屬的共課結果，不含同伴私有資料。Supabase 私有 schema、API 角色權限、跨 Workspace 404 與公開連結 allowlist 均維持現有邊界。

## 7. Contract 凍結前的兩個決定

1. **Roadmap 歸屬與順序（Product Owner）**：建議獨立的「學生群組」Contract → Sol → CI 套件，在已交付的個人課與 M8-E 支付主幹之外並行；共用 migration／Module 接口的整合須序列化。現行 Roadmap 第 6 節禁止新增編號插入 M10 以前，下一個新階段須由 M11 起命名；數字階段同時代表整合／發布次序，而 M9、M10 尚未完成／決定。因此 PO 須同時選定群組套件的階段與對 M9／M10 的整合次序，不能只命名 M11 就默認可提前發布。此稿不自行編號或更改已核准 Roadmap。只有 PO 批准套件位置及凍結此 Contract 後才可進 Sol。
2. **最小資料主體可行性（工程檢查）**：第 6 節已列出 Main 的主要受影響路徑，受型別約束的既有主體是可執行候選；Sol 起始時須完成逐查詢清單、DB 約束與無資料變更的 migration 檢查。能用明確型別與聚焦測試隔離則採候選；若不能，在正式寫入群組資料前提出獨立 group 主體的具體差異回 Contract。此為工程可判斷的 gate，無須 PO 回答假設題。
