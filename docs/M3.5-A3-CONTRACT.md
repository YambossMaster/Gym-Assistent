# M3.5-A3 Contract — Student roster, detail, and Lesson Purchase correction

> Frozen 2026-09-13. This Contract implements the approved M3.5-A3 Roadmap scope. Product Owner
> explicitly approved deferring nearest future session and dated Course Session history to M4; it
> does not introduce scheduling data or change the M4 ownership boundary.

## 1. Coach job and route boundary

A signed-in Coach needs to locate an active or archived Student, understand current lesson
entitlement, keep Coach-only context with the Student record, and correct an erroneous Lesson
Purchase without silently replacing the current server record.

| Surface         | Frozen responsibility                                                                                                                                       |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/students`     | Browse active or archived Students, search the selected view, and see each Student's current lesson summary.                                                |
| `/students/:id` | Read/edit existing Student identity and private context; read entitlement and the Coach-only Purchase ledger; create, correct, or delete a Lesson Purchase. |

The existing create-Student operation remains available, and an initial Purchase may be recorded
after it. Fixed rhythm, availability, next-session information, Schedule Series, dated Course
Session history, Training performance, notifications, public links, and payments are out of scope.

## 2. Demo reference and deliberate deviations

The archived Demo supplies the product reference for active/archive roster views, search, lesson
account, low-balance attention, Student private context, and editable Purchase ledger. It is not
persistence authority.

- A3 renders no next-session card or dated Course Session history. M3 `course_session` rows contain
  only Workspace/Student ownership and status; date, time, location, and future occurrence would be
  fabricated. M4 owns the necessary scheduling projection.
- Fixed-rhythm, Schedule Series, performance, LINE/reminder, and scheduling actions remain absent.
- The API derives `remaining = purchased - completed`; zero and negative balances remain visible,
  do not block an action, and do not trigger an automatic repair.
- Private notes, phone, and linked-status remain authenticated Coach-only fields and are never a
  public capability projection.

## 3. Projection and authorization contract

Every operation verifies the Coach and derives the Workspace on the server. The browser never sends
a Workspace ID. A Student or Purchase absent from that Workspace, including another Coach's data,
returns `404` without resource detail.

### `GET /v1/students`

The response remains `{ students }`. Each existing Student gains the additive field:

```ts
lessonSummary: {
  purchased: number
  completed: number
  remaining: number
}
```

`purchased` is the sum of the Student's Lesson Purchase counts, `completed` is the count of existing
`course_session` rows whose status is `completed`, and `remaining` is their difference. The roster
has no `nextSession` field in A3.

### `GET /v1/students/:studentId`

The response remains `{ detail }` with `student`, `purchases`, and `lessonSummary`. Each Purchase
gains additive `version: number`. Purchases are newest-first by `purchasedAt`, then ID descending,
for a deterministic ledger. There is no Course Session list or next-session field in A3.

### Lesson Purchase mutations

`POST /v1/students/:studentId/lesson-purchases` remains unchanged except its returned Purchase
includes `version`.

`PATCH /v1/students/:studentId/lesson-purchases/:purchaseId` accepts exactly:

```ts
{
  purchasedAt: string // ISO-8601 instant with offset
  lessonCount: number // integer 1..10000
  amountMinor: number // integer 0..999999999999
  currency: string // uppercase ISO-4217 three-letter code
  privateNote?: string // trimmed, maximum 4000 characters
  version: number // positive integer
}
```

It replaces all editable Purchase fields only if it belongs to the verified Workspace and its version
matches; it returns `{ purchase }` with an incremented version. It cannot edit Student identity,
completed sessions, or another Purchase.

`DELETE /v1/students/:studentId/lesson-purchases/:purchaseId` accepts exactly
`{ confirmation: 'DELETE', version: number }`, permanently removes the matching Workspace-owned
Purchase, and returns `204`. Explicit confirmation is required because it changes entitlement and
manual-income summaries.

Every accepted Purchase create/update/delete is reflected through the server-derived summary on the
next projection read. No stored balance, client-side arithmetic authority, automatic replacement,
or cross-Student transfer is permitted.

### Version and errors

One serialized M3.5 migration adds non-null positive Purchase `version`, initializing all historical
rows to `1`. Successful updates increment only that Purchase version. A stale PATCH or DELETE returns:

```ts
{
  error: 'version_conflict',
  reason: 'lesson_purchase_version_conflict',
  message: string,
  currentPurchase: LessonPurchase
}
```

`currentPurchase` is returned only after the same Workspace check and includes only the authorized
Coach-facing Purchase fields necessary to reapply an intended edit. Missing/cross-Workspace Student
or Purchase returns non-enumerating `404`; malformed input returns `400 invalid_request`; invalid
identity returns `401`; operational failures return `5xx` without internal detail.

## 4. Route states and cache contract

All server data uses the existing Coach-scoped TanStack Query key factory, stays in memory, and is
cleared on Auth subject change or sign-out.

| Surface         | Loading / ready / refreshing                                                              | Empty / not found / error                                                                                                                                                          | Mutation / conflict                                                                                                                                                                           |
| --------------- | ----------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Roster          | First request has a roster Loading boundary; cached cards remain readable during refresh. | First active view: first-Student Empty with create action. Empty archive view: filter Empty. Nonblank search with no match: search Empty with clear-search action. Failure: retry. | Student archive/restore keeps only its control pending and invalidates roster/detail.                                                                                                         |
| Detail          | First request has detail Loading; cached detail remains readable during refresh.          | `404` is terminal Not Found; transport failure is recoverable Error; missing private note is a local absence state.                                                                | Existing Student mutations retain input on validation, transport, or Student-version conflict.                                                                                                |
| Purchase ledger | Ledger reads with detail data in deterministic order.                                     | No Purchases is ledger Empty with record-Purchase action.                                                                                                                          | Create/edit/delete disable only their active submit/confirmation action and retain input on failure. A `409` keeps the draft, presents current Purchase, and requires explicit reapplication. |

Successful Student or Purchase mutations invalidate this Coach's roster and detail keys. Purchase
mutations also invalidate manual-income. A3 invalidates no Today/Calendar key because M4 owns those
projections. Existing authorized detail prefetch may continue only for roster Students.

## 5. Product, interaction, and copy decisions

On desktop and exact 390×844 mobile, `/students` places active/archive controls and search before
the roster. Each roster item shows identity, optional goal, and the lesson summary with Sol-provided
low/negative attention, never a scheduling claim. `/students/:id` places identity/actions before
entitlement, Coach-only private context, and the Purchase ledger. The ledger supports new, edit,
and delete actions. Delete requires literal `DELETE` confirmation.

At 390×844 every form, recovery action, and delete confirmation remains reachable above the
safe-area-aware bottom navigation without horizontal overflow. Keyboard users can reach all controls.
Opening a destructive dialog focuses its confirmation input; Escape/Cancel closes it and restores
focus to the initiating control.

Sol supplies concise Traditional Chinese copy for roster controls and Empty states, the lesson
account and truthful low-balance attention, the Coach-only notice, and Purchase validation/error/
stale-version/delete-confirmation states. Rendered copy must not claim calendar state, next session,
schedule synchronization, performance data, milestones, cache state, or unavailable features.

## 6. Terra implementation and test boundary

Terra may create the Purchase-version migration; extend Student/Lesson Module, adapters, HTTP
schemas/routes, typed client, queries/mutations, semantic unstyled route states, and deterministic
fixtures. Terra may not choose layout, spacing, colour, typography, responsive composition,
interaction styling, animation, or end-user copy.

Required evidence:

1. Module, PostgreSQL adapter, and HTTP tests prove Workspace derivation, two-Coach list/detail/
   Purchase isolation, additive roster summary, historical version initialization, and balance
   recalculation after create/update/delete, including negative balances.
2. HTTP tests prove validation, cross-Workspace `404`, stale PATCH/DELETE `409` with only current
   authorized Purchase, and rejection of browser-supplied Workspace IDs.
3. Focused Web tests prove first/filter/search Empty selection, first-load/cached-refresh/error/not-
   found states, Purchase pending/error/conflict recovery, and roster/detail/income invalidation.
4. Sol browser acceptance proves desktop and exact 390×844 behaviour, keyboard/focus/delete-dialog
   behaviour, no horizontal overflow, and no fabricated scheduling/performance content.
5. CI runs focused tests plus root `npm run check`, `npm run build`, `git diff --check`, applicable
   two-Coach live/browser evidence, migration dry-run, Supabase advisors, one cohesive commit/push,
   and confirmed remote Verify and migration-dry-run jobs.
